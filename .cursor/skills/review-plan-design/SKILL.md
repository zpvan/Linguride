# 方案设计审查 (Plan Design Review)

在 plan 模式中完成方案设计后，对方案进行系统性审查。目标是确保方案的每个关键部分都是清晰、明确、无矛盾的，可以直接进入实施阶段。

## 审查流程

### Step 1: 收集方案全貌

回顾当前对话中产出的完整方案，包括：
- 功能需求描述
- 架构设计 / 模块划分
- 数据流 / 交互流程
- 技术选型决策
- 文件变更清单（如有）

### Step 2: 逐维度审查

按以下 6 个维度逐项检查，对每个维度给出明确结论。

#### 2.1 架构设计

- [ ] 模块划分是否合理，层次关系是否清晰
- [ ] 数据流向是否有明确路径，无死角
- [ ] 是否存在跨层调用或违反架构分层的设计

#### 2.2 模块职责

- [ ] 每个模块/组件的职责是否有清晰的一句话定义
- [ ] 是否存在职责重叠（两个模块做同一件事）
- [ ] 是否存在职责真空（某件事没有模块负责）
- [ ] 单个模块是否承担了过多职责

#### 2.3 接口定义

- [ ] 模块间的通信方式是否明确（函数调用 / 消息传递 / 事件等）
- [ ] 关键接口的输入输出是否有定义（参数、返回值、类型）
- [ ] 接口契约是否完整（错误码、异常情况的处理约定）

#### 2.4 依赖关系

- [ ] 模块间的依赖方向是否合理（高层依赖低层，而非反向）
- [ ] 是否存在循环依赖
- [ ] 外部依赖（第三方库、API）是否明确，版本/能力约束是否考虑
- [ ] 耦合度是否可接受，是否有不必要的紧耦合

#### 2.5 边界情况

- [ ] 异常处理策略是否明确（失败时如何表现）
- [ ] 降级/兜底方案是否考虑（依赖不可用时的行为）
- [ ] 并发/竞态条件是否考虑（如适用）
- [ ] 数据边界是否考虑（空值、极端值、大数据量）

#### 2.6 一致性

- [ ] 命名规范是否统一（文件名、变量名、类型名）
- [ ] 设计模式是否一致（相似问题是否用相似方案解决）
- [ ] 方案中的术语是否前后一致，无歧义
- [ ] 与项目现有代码的风格/模式是否保持一致

### Step 3: 输出审查报告

使用以下格式输出结果：

```
## 方案审查报告

### 审查结论: [通过 / 有待澄清 / 需要修改]

### 各维度评估

| 维度 | 状态 | 说明 |
|------|------|------|
| 架构设计 | [清晰/模糊/冲突] | 简要说明 |
| 模块职责 | [清晰/模糊/冲突] | 简要说明 |
| 接口定义 | [清晰/模糊/冲突] | 简要说明 |
| 依赖关系 | [清晰/模糊/冲突] | 简要说明 |
| 边界情况 | [清晰/模糊/冲突] | 简要说明 |
| 一致性   | [清晰/模糊/冲突] | 简要说明 |

### 发现的问题（如有）

#### [问题编号] [问题标题]
- **维度**: 所属审查维度
- **严重程度**: 阻塞 / 需讨论 / 建议优化
- **描述**: 具体问题描述
- **建议**: 修改建议或需要用户回答的问题
```

### Step 4: 向用户提问

如果发现模糊或冲突之处，使用 AskQuestion 工具（如可用）或直接提问：

- **模糊点**: 方案中未明确说明的设计决策，需要用户确认意图
- **冲突点**: 方案中自相矛盾的描述，需要用户澄清以哪个为准
- **遗漏点**: 方案未覆盖但实施时必须面对的问题

每个问题应当：
1. 准确引用方案中的相关描述
2. 说明为什么这里需要澄清
3. 如可能，提供选项供用户选择

## 审查原则

- **不做过度设计审查**: 只关注当前方案范围内的问题，不建议超出范围的优化
- **务实优先**: 区分"必须澄清才能实施"和"有则更好"的问题
- **尊重已有决策**: 对方案中已明确做出的技术选型不质疑，除非发现明显矛盾
- **聚焦可实施性**: 审查的最终目标是确保方案可以无歧义地转化为代码
